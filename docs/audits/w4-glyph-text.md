# W4 — glyph-outline text (slice 2): the page seam, the proof, and the bug it caught

**Status:** SLICE 2 LANDED — the committed glyph table (step 1, 5fbd134), the consumer seam (step 2, d5afb69), and the proof that forced the last wiring into the open (this commit). Slice 3 — the captions-lane ASR wiring — is specced in `docs/design/s120-2d-animation-roadmap.md` §3 W4 and is NOT claimed here.

## What slice 2 is

Per-asset `textMode: "glyph"` swaps an asset's `<text>` elements for committed-outline paths **at registration** (the single-face route, reconciliation decision §10.3 — Caveat, OFL, vendored at `public/fonts/caveat/`, outlines generated by `scripts/w4-generate-glyphs.py` into `src/lib/tubeforge/whiteboard/glyphs.ts`). Everything downstream rides the ordinary path machinery: `buildGeometry` sees ordinary paths, `scheduleScene` emits `draw_path` rows (the pen lane), `wb-page` namespaces and dash-animates them through the existing draw law, the W5 camera frames their bboxes like any other stroke, and the fill rides the engine's uniform fill law. Filled faces contour letters in parts, so each outline is split per subpath — the S67 single-subpath seam law holds and the hand walks contours like a multi-stroke letter. Two-level honest fallback: per-text (uncovered chars, degenerate geometry, or a non-paint fill) keeps the `<text>` element byte-for-byte; per-asset (no metadata) never applies the transform.

## The proof's find — rows pointed at elements that did not exist

`scripts/w4-glyph-proof.mts` (the slice-2 exit gate, modeled on the W1/W5 harnesses) renders a project that USES the glyph-mode asset through the real engine at all three aspects, beside a marker-mode text card in the same scene. Its first run failed the only honest way:

- **Structural layer green:** registration produced the contour paths, the engine's own schedule (`beatSceneEvents` — the exact call `render.ts` makes) emitted `draw_path` rows for them and no `write_text` row, readability passed per aspect.
- **Pixel layer red:** the word region gained only ~12% ink across the glyph draw window — and the evidence JPEGs showed the truth: the 12% was the resting HAND. The word never rendered at all.

Root cause: `loadLibrary`'s `register` kept the RAW svg in the `assets` map (what `composeScene` embeds — for the render engine AND the editor canvas) while only `extracted` saw the transformed markup. The scheduler's rows pointed at page elements that did not exist; the raw `<text>` was hidden by the applier (no `write_text` event ever comes) and stayed hidden forever. The step-2 unit battery pinned registration and scheduling but nothing looked at the composed page — exactly the "pins that LOOK at pixels" class the roadmap's W4 `wb-page.ts` row demands.

**The fix:** `assets.set(a.id, effective)` — the page seam rides the transformed svg. Non-glyph assets store the same object (`effective === a`), byte-identical by construction; the W1 harness 16:9 gate re-run GREEN against the frozen baseline after the fix (912/912 decoded frames, all lenses green — zero benchmark pixels moved). A new unit pin closes the layer gap: the composed page for a glyph-mode placement exposes the contour elements, carries no zombie `<text>`, and the marker card's texts still ride the page's text index.

## Honest edges

- **No kerning (GPOS).** Plain advances only — the marker hand tolerates it; the fit check to re-open this is when a tracked label meets a tight crop.
- **Contour order is document order** — the pen walks each glyph's parts in the order the generator emitted them. No stroke-order intelligence (that is W7's hand-realism lane, not slice 2).
- **The preview pass scope:** the composed page + the shared applier at the settled frame, screenshotted headlessly. The studio's interactive canvas imports the SAME `composeScene`/`loadLibrary` map, so the fix repairs it by construction — but no human has eyeballed the studio UI in this slice.
- **Slice 3 is not here.** Production text is still marker-mode everywhere except `glyph-note`; the captions-lane ASR wiring (anchors → the spoken-window schedule) is the next slice, and the estimator fallback remains byte-identical (pinned).
